# MCARE 홈페이지 제작 표준 v1.0

> **이 문서는 MCARE AI OFFICE에서 제작·관리하는 모든 홈페이지에 적용하는 공식 개발 규칙입니다.**
>
> 신규 홈페이지 제작, 기존 홈페이지 개편, 랜딩페이지, SEO 개선, 기능 추가, 디자인 변경,
> 관리자 기능 추가 작업을 시작하기 전에 **먼저 이 문서를 확인**합니다.

|---|---|
| 버전 | v1.0 |
| 제정일 | 2026-08-15 |
| 적용 대상 | MCARE AI OFFICE가 제작·관리하는 모든 웹 프로젝트 |

## 0. 이 문서를 쓰는 법

**모든 항목을 무조건 구현하지 않습니다.** 프로젝트 성격에 따라 판단합니다.

| 표시 | 뜻 |
|---|---|
| **[필수]** | 어떤 프로젝트든 반드시 적용 |
| **[해당 시]** | 그 기능·콘텐츠가 실제로 있을 때만 적용 |
| **[불필요]** | 이 프로젝트에는 해당 없음 — 작업계획에 그렇게 적고 넘어감 |

### 과잉 구현 금지

- 단순 랜딩페이지에 관리자 CMS를 억지로 만들지 않습니다.
- FAQ가 없는 페이지에 `FAQPage` 스키마를 만들지 않습니다.
- 후기가 없는데 `Review`/`AggregateRating` 스키마를 넣지 않습니다.
- 지점이 하나뿐인데 복잡한 다지점 구조를 만들지 않습니다.

### 프로젝트 유형별 최소 적용 기준

| 유형 | 반드시 | 보통 생략 |
|---|---|---|
| 랜딩페이지 1장 | SEO 메타·OG·성능·접근성·전환이벤트 | CMS, sitemap, 다국어, Breadcrumb |
| 회사 홈페이지 | 전 항목 대부분 | 전자상거래 스키마 |
| 사내 도구·관리자 | 접근성·성능·기존기능보호 | SEO 전반 (검색 노출 차단이 정답) |
| 기존 사이트 개편 | 위 + **301 매핑**·회귀검사 | — |

## 1. 작업 시작 전 절차 [필수]

홈페이지 관련 작업은 **예외 없이** 이 순서로 진행합니다.

```
현재 정상 상태 확인
  → 복구 지점 확보 (태그/브랜치/백업)
  → 별도 작업 브랜치 생성
  → 작은 단위로 변경
  → 테스트
  → 기존 기능 회귀검사
  → SEO 검사
  → 모바일 검사
  → 성능 검사
  → 문제 없을 때만 반영
```

**운영 중인 main 또는 실서비스를 직접 수정하지 않습니다.**

## 2. SEO 기본 표준

### 2-1. 페이지별 개별 설정 항목 [필수]

주요 페이지와 게시물마다 아래를 **개별로 지정할 수 있어야** 합니다.

| 항목 | 비고 |
|---|---|
| SEO Title | |
| Meta Description | |
| URL Slug | |
| H1 | |
| 대표 이미지 | |
| 이미지 ALT | |
| Canonical URL | |
| 검색엔진 노출 여부 | noindex 제어 |
| Open Graph 제목 | |
| Open Graph 설명 | |
| Open Graph 이미지 | |

> CMS가 없는 정적 페이지라면 "페이지 파일마다 지정 가능"하면 충족입니다.

### 2-2. 기본값 자동 생성 [필수]

관리자가 입력하지 않았을 때, **페이지 제목과 실제 본문**을 이용해 안전한 기본값을 만듭니다.

- Title 미입력 → `페이지 제목 | 회사명`
- Description 미입력 → 본문 앞부분에서 추출 (문장 중간에서 자르지 않음)
- OG 이미지 미입력 → 회사 기본 공유 이미지

**본문에 없는 내용을 지어내지 않습니다.**

### 2-3. 제목 구조 [필수]

- 페이지당 **H1은 1개**
- 하위 제목은 **H2 → H3** 순서를 건너뛰지 않음
- 디자인 때문에 제목 태그를 쓰지 않음 (크기는 CSS로 조절)

### 2-4. 텍스트로 제공 [필수]

**핵심 콘텐츠를 이미지 속 글자로 대체하지 않습니다.** 검색엔진과 AI가 읽을 수 있는 실제 HTML 텍스트로 제공합니다.

### 2-5. Semantic HTML [필수]

`header` `nav` `main` `article` `section` `aside` `footer` 를 의미에 맞게 사용합니다.
`div` 로만 이루어진 구조를 피합니다.

## 3. 검색엔진 크롤링 [해당 시]

검색 노출이 필요한 프로젝트에서 검토합니다.

| 항목 | 확인 내용 |
|---|---|
| `sitemap.xml` | **실제 공개 콘텐츠만** 포함 |
| `robots.txt` | 관리자·테스트·비공개 경로 차단 |
| canonical | 중복 URL 정리 |
| 404 페이지 | 안내와 이동 경로 제공 |
| 301 redirect | 주소 변경 시 필수 |
| HTTPS 통일 | http → https |
| www 통일 | www 또는 non-www 하나로 |
| 중복 URL 방지 | 슬래시 유무, 대소문자, 파라미터 |
| 공개/비공개 분리 | 색인 정책을 명확히 |

**관리자 페이지·테스트 페이지·비공개 콘텐츠는 검색엔진에서 제외합니다.**

## 4. URL 표준 [필수]

짧고 사람이 이해할 수 있는 주소를 씁니다.

```
좋음                          피함
/company                      /page.php?id=12
/business                     /sub/sub2/sub3/index.html
/business/interior            /bbs/board.php?bo_table=notice&wr_id=88
/projects                     /제품소개%20페이지
/projects/project-name
/news
/contact
```

- 의미 없는 숫자, 긴 쿼리 파라미터, 불필요한 특수문자를 피합니다.
- 한글 URL은 공유·추적 시 깨질 수 있어 영문 슬러그를 권합니다.

### 개편 시 [해당 시]

기존 사이트를 개편할 때는 **이전 주요 URL을 먼저 조사**하고, 필요하면 **301 redirect 매핑표**를 만듭니다. 이 조사를 건너뛰면 기존 검색 순위를 잃습니다.

## 5. 이미지 SEO

| 구분 | 규칙 | 등급 |
|---|---|---|
| 콘텐츠 이미지 | 내용을 설명하는 구체적 ALT | [필수] |
| 장식 이미지 | `alt=""` (빈 값) | [필수] |
| 파일명 | 의미 있는 영문 이름 | [필수] |
| 포맷 | WebP/AVIF 우선 검토 | [해당 시] |
| responsive images | `srcset`/`sizes` | [해당 시] |
| 자동 resize·압축 | 업로드 파이프라인 | [해당 시] |
| lazy loading | 화면 밖 이미지에 적용 | [해당 시] |

### 반드시 지킬 두 가지 [필수]

1. **첫 화면 핵심 이미지(LCP 후보)에는 lazy loading을 걸지 않습니다.** 오히려 느려집니다.
2. **`width`/`height` 또는 `aspect-ratio`를 지정합니다.** 레이아웃이 밀리는 현상(CLS)을 막습니다.

## 6. 구조화 데이터 (JSON-LD) [해당 시]

**실제 페이지 내용과 일치하는 것만** 넣습니다.

| 스키마 | 적용 시점 |
|---|---|
| `Organization` | 회사 홈페이지 |
| `LocalBusiness` | 오프라인 주소·영업시간이 있을 때 |
| `BreadcrumbList` | 계층 구조가 있을 때 |
| `Article` | 뉴스·블로그 글 |
| `FAQPage` | **실제 FAQ 섹션이 화면에 있을 때만** |
| `Service` | 서비스 소개 페이지 |
| `WebSite` / `WebPage` | 기본 |

### 금지 [필수]

**존재하지 않는 후기, 평점, 가격, 수상내역을 SEO 목적으로 만들어내지 않습니다.**
구조화 데이터와 화면에 보이는 내용은 **반드시 일치**해야 합니다. 불일치는 검색엔진 제재 대상입니다.

## 7. SNS 공유 [필수]

- 페이지별 Open Graph 정보 제공
- 대표 이미지가 없으면 **회사 기본 공유 이미지**로 대체
- 카카오톡·네이버·주요 SNS에서 제목·설명·이미지가 정상 표시되는 구조

> 카카오톡은 자체 캐시가 있어, 수정 후에도 이전 정보가 보일 수 있습니다. 배포 후 캐시 초기화를 확인합니다.

## 8. 분석·광고 연동 준비 [해당 시]

아래를 **쉽게 붙였다 뗄 수 있는 구조**로 만듭니다.

Naver Search Advisor · Google Search Console · GA4 · Google Tag Manager ·
Naver Analytics · Naver 광고 전환 · Kakao Pixel · Meta Pixel

### 핵심 규칙 [필수]

**사이트 인증값이나 추적 ID를 소스코드 여러 곳에 하드코딩하지 않습니다.**
환경변수 또는 관리자 설정 등 **한 곳에서 관리**합니다.

이유: 나중에 값을 바꿀 때 누락이 생기고, 실수로 공개 저장소에 올라갈 위험이 커집니다.

## 9. 전환 이벤트 표준 [해당 시]

문의·상담이 있는 사이트라면 아래 행동을 **구분해서** 추적할 수 있게 설계합니다.

| 이벤트 | 대상 |
|---|---|
| 견적 문의 완료 | 폼 제출 성공 |
| 사업 문의 완료 | 폼 제출 성공 |
| 전화 클릭 | `tel:` 링크 |
| 이메일 클릭 | `mailto:` 링크 |
| 카카오 상담 클릭 | 채널 링크 |
| 길찾기 클릭 | 지도 링크 |
| 회사소개서 다운로드 | 파일 링크 |
| 카탈로그 다운로드 | 파일 링크 |
| 기술자료 다운로드 | 파일 링크 |

### 구현 규칙 [필수]

- 버튼·폼에 **의미 있는 `id` 또는 `data-*` 속성**을 붙입니다.
- 이벤트 이름은 **프로젝트 전체에서 일관되게** 관리합니다 (한 곳에 정의).

## 10. 웹접근성·웹표준 [필수]

| 항목 | 확인 |
|---|---|
| ALT | 콘텐츠 이미지에 적절히 |
| `label` ↔ `input` 연결 | `for`/`id` 또는 감싸기 |
| 키보드 이동 | 마우스 없이 모든 기능 사용 가능 |
| 명도 대비 | 본문 4.5:1 이상 권장 |
| 터치 영역 | 모바일에서 충분히 크게 |
| `button` vs `a` | 동작=button, 이동=a |
| 제목 계층 | H1→H2→H3 |
| 모바일 가독성 | 본문 16px 이상 권장 |
| focus 표시 | 지우지 않기 |
| semantic HTML | 위 2-5 참조 |

## 11. 모바일 우선 성능 [필수]

**디자인보다 실제 사용성과 속도를 우선합니다.**

### 이미지
WebP/AVIF 우선 검토 · responsive image · resize · 압축 · lazy loading ·
**LCP 이미지는 우선 로딩**

### 영상 [해당 시]
모바일 대체 이미지 또는 경량 영상 · `poster` 지정 · 필요할 때만 플레이어 로딩 ·
YouTube 등 iframe은 **클릭 후 로딩(click-to-load)** 검토

### 코드
쓰지 않는 JS/CSS 최소화 · code splitting · `defer`/`async` ·
중복 라이브러리 방지 · 과도한 애니메이션 방지

### 폰트
사용하는 family/weight 최소화 · `font-display: swap` ·
필요한 폰트만 preload · **한글 subset 검토** (한글 폰트는 용량이 큼)

### 캐시 [해당 시]
정적 자산 장기 캐시 · 파일 fingerprint/버전 관리 · Brotli/Gzip · CDN 가능 구조

## 12. Core Web Vitals 목표

모바일 기준:

| 지표 | 목표 | 뜻 |
|---|---|---|
| LCP | ≤ 2.5초 | 가장 큰 요소가 보이기까지 |
| INP | ≤ 200ms | 클릭 후 반응 속도 |
| CLS | ≤ 0.1 | 화면이 밀리는 정도 |

PageSpeed 모바일 성능 **80점 이상**을 우선 목표로 합니다.

### 중요 [필수]

**점수를 억지로 맞추려고 사용자 경험이나 필수 기능을 훼손하지 않습니다.**
이 수치는 목표값이며, 외부 서비스(지도·채팅·광고 스크립트)와 실제 서버 환경을 고려해 검증합니다.

## 13. AEO / GEO / AI 검색 최적화 [해당 시]

ChatGPT·Gemini·Perplexity 등 AI 기반 검색이 회사 정보를 정확히 이해하도록 만듭니다.

> **전제**: 특정 AI 서비스의 노출이나 인용을 보장한다고 가정하지 않습니다.
> 우리가 할 수 있는 것은 "정확하게 이해되기 쉬운 구조"를 만드는 것까지입니다.

| 원칙 | 내용 |
|---|---|
| 회사명 명확 | 페이지마다 회사명이 분명히 드러남 |
| 브랜드↔사업 관계 | 어떤 회사가 어떤 사업을 하는지 명시 |
| 서비스별 독립 설명 | 각 서비스가 그 페이지만 봐도 이해됨 |
| 서비스 지역 명시 | 어디까지 가능한지 |
| 핵심 정보 일관성 | 주소·연락처가 모든 페이지에서 동일 |
| 실제 사례 강화 | 실제 프로젝트 콘텐츠 |
| FAQ 콘텐츠 | 실제 고객 질문 기반 |
| 직접 답하는 문장 | 질문에 바로 답하는 구조 |
| 전문 용어 설명 | 업계 용어에 짧은 설명 |
| 작성·검수 주체 | 필요한 콘텐츠에 명시 |
| 업데이트 날짜 | 중요한 경우 표시 |
| Breadcrumb | 위치 파악 가능하게 |
| Entity 관계 | 회사–서비스–지역–사례 연결 구조 |
| 데이터↔화면 일치 | 구조화 데이터와 실제 내용 동일 |
| JS 의존 최소화 | **중요 정보가 JS 실행 후에만 나타나는 구조를 피함** |
| AI 크롤러 정책 | robots 정책과 함께 명시적으로 관리 |

### 금지 [필수]

**단순 키워드 반복이나 AI 검색을 속이기 위한 문장을 만들지 않습니다.**

## 14. 콘텐츠 신뢰성 [필수]

**확인되지 않은 정보를 임의로 만들어내지 않습니다.**

### 우선 활용할 것
실제 회사 정보 · 실제 사업 내용 · 실제 작업 사례 · 실제 사진 ·
실제 서비스 지역 · 실제 경력 · 실제 인증/자격 · 실제 고객 질문 · 실제 기술자료

### 절대 만들어내지 않을 것
확인되지 않은 **숫자·수상내역·고객수·후기·평점**

자료가 없으면 **"자료 필요"로 표시하고 대표에게 요청**합니다. 빈칸을 그럴듯한 문장으로 채우지 않습니다.

## 15. 기존 기능 보호 규칙 [필수] ★ 가장 중요

### 작업 순서

```
현재 정상 상태 확인 → 복구 지점 확보 → 별도 작업 브랜치
  → 작은 단위 변경 → 테스트 → 기존 기능 회귀검사
  → SEO 검사 → 모바일 검사 → 성능 검사 → 문제 없을 때만 반영
```

### 금지

- 새 기능 때문에 **기존 기능을 임의로 삭제하거나 대규모 재작성하지 않습니다.**
- 정상 작동 중인 코드를 이유 없이 전면 리팩터링하지 않습니다.
- 기존 구조를 바꿔야 한다면 **영향 범위를 먼저 조사**합니다.

### 별도 안전 절차가 필요한 위험 변경

환경변수 · DNS · 배포 설정

## 17. 이 표준의 자동 적용

홈페이지 관련 작업을 시작할 때 **이 문서를 먼저 확인**합니다. 구체적인 절차는
저장소 루트의 **`CLAUDE.md`** 에 기재돼 있으며, Claude Code가 작업 시작 시 자동으로 읽습니다.

작업계획서에는 다음을 명시합니다.

```
적용: (해당 항목 번호)
해당 시 적용: (조건부 항목)
불필요: (제외 항목과 그 이유)
```

**제외한 항목은 반드시 이유를 적습니다.** "빠뜨린 것"과 "판단해서 뺀 것"을 구분하기 위해서입니다.
